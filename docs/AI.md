# AI 建模：让模型决定怎么建

> 目标：题干 → 模型这条链路，从「关键词 + 正则」升级成「让模型读题、决定用哪个场景、填哪些参数」。
> 但**决定权仍然收在一个窄接口里**——LLM 只能从已有模型里选、或按已有基元拼，不能凭空写场景。

---

## 1. 为什么不让 LLM 直接吐 Scene JSON

Scene 有几十个字段、几百行。让模型直接写，最常见的失败是「看着像但跑不起来」：
坐标是错的、约束引用不存在的 body、`params` 和 `layout()` 打架。而我们**没有自动判断对错的能力**——
这正是产品最怕的事：给一个错模型，学生还以为是对的。

所以把 LLM 的作用限定在**做决定**，三种模式：

| mode | 它做什么 | 我们做什么 | 为什么可靠 |
|---|---|---|---|
| `preset` | 选一个已有场景 + 填参数 + 勾开关 | 走 `preset.build()` + `layout()` | 几何一定合法；参数被夹在可调区间内 |
| `chain` | 给出阶段序列（斜面/水平/圆弧/上坡） | 走 `buildChain()` | 基元有限、首尾自动相接 |
| `build` | 发一串搭建指令（加物体/加约束/加场） | 走 `sceneFromOps()` + 结构校验 | 只能引用端口，不许算坐标；产出后立刻验算 |
| `unsupported` | 说明缺哪类建模 | 拒绝 + 给手动入口 | 不猜、不近似 |

### build 模式：给 agent 的「简化子集」

这一条借的是 **Base Modelica** 的思路——一个 25 年的语言社区为了机器可读，专门做了个简化子集。
我们对应的是 `BuildOp`：只有三种指令，参数受约束，**不许写代码、也不许直接吐 Scene JSON**。

```json
{"op":"addBody","id":"block","shape":{"kind":"rect","w":0.2,"h":0.15},
 "at":{"x":0,"y":0.1},"behavior":"moving","mass":0.5,"friction":0.2}
{"op":"addConstraint","type":"rope","a":{"body":"ball","port":"top"},"b":{"world":{"x":0,"y":2}}}
{"op":"addField","type":"E","magnitude":40,"angleDeg":90}
```

三条规矩：

1. **只能从这三个 op 里选**；
2. **两端只能引用端口**（`center/top/bottom/left/right/四角`，或物体自己声明的 `axle/hook`），
   不许算坐标——模型不知道场景尺度，给绝对坐标就会造出悬空的球；
3. **参数只填题干给的**，缺的走默认值。

`behavior` 用生活语言而不是引擎术语：`fixed`（固定地形）/ `moving`（会动）/ `rolling`（滚动的刚体）/
`sliding`（匀速平移）。模型不需要知道 `static` 和 `particle` 的区别。

产出后立刻过 `analyzeScene()`：悬空端口、退化几何、过约束、马达装在锁转动的物体上——全部变成
warnings 带回去。**这是「agent 出招后自己验算」那一环**，也是它敢开放搭建权限的前提。

实测（glm-4.6，题干：「水平传送带以 2 m/s 匀速向右运动，把物块轻放在左端，动摩擦因数 0.2」）：

![AI 用 build 指令搭出来的传送带：物块被带面摩擦推着加速](screenshots/260-ai-belt.png)

它给出了 `belt`（固定线）+ `belt` 约束（speed=2）+ `block`（带 μ=0.2）三条指令，
仿真里物块以 μg ≈ 1.96 m/s² 加速——和手算一致。**这类题之前是明确拒绝的。**

三种都落到**同一条既有契约** `ParseResult`（见 `core/problem.ts`），所以上层 UI、题库状态、
回退逻辑一行都不用改——这也是这次能一周内接进来的原因。

## 2. 三道保险

「接了 AI 反而更容易出错」是这类改造的典型翻车方式。所以：

1. **没配 key** → **明确告诉用户缺什么**（用户页 →「AI 建模」），并提示可以手动搭。
   **不再有第二套生成器兜底**——2026-10-26 删掉了规则解析（见 §2.5）。
2. **请求失败**（超时、余额不足、返回的不是 JSON、选了不存在的场景）→ 明确报错、把题存进「我的题目」、
   指路手动搭。`shots-bank.mjs` 有断言锁这个：塞假 key，要求「报错 + 存题 + 不建模型」。
3. **AI 明确说 unsupported** → 按拒绝处理。题库详情页的按钮会变成「手动搭 →」，点开是空白画布。

### 2.5 规则解析去哪了

原来有两条生成路：离线的 `parseProblem`（关键词 + 正则）和有 key 时的 AI。**规则路已经删掉。**

理由：
- 两套生成器意味着**两套边界**。规则拒绝的题 AI 可能能建，用户看到的是"同一个按钮，有时行有时不行"。
- 规则路只认 8 类原型，遇到多过程就拒绝——它给出的"确定性"是**假的安全感**。
- 维护成本：题库状态、9 道真题回归、分享串测试全都挂在它身上，而它本身的覆盖率是 11%。

代价（明确接受）：
- **题库的「可建模 / 暂不支持」变成人工标注**，不再有自动验证。AI 能力在变，静态标注本来就会过时；
  真正的边界应该靠 `scripts/ai-check.mjs` 定期打真实接口来测。
- **没配 key 就完全不能自动建模**。这是 BYO-key 的必然结果，所以编辑器兜底必须好走——
  详情页的「手动搭 →」就是为此加的。
- 小程序端**彻底没有生成能力**（它本来就调不了 AI）。题库和建模库照常，画布照常能手动搭。

## 3. 服务商与跨域：各家不一样，不能一刀切

**跨域策略决定要不要转发层**，而各家不一样（都实测过）：

| 服务商 | 端点 | 浏览器能直连吗 | 需要转发 |
|---|---|---|---|
| **智谱 GLM（Coding Plan）** | `/llm/chat/completions` → `open.bigmodel.cn/api/coding/paas/v4` | ❌ 预检不回 ACAO | ✅ |
| **DeepSeek** | `https://api.deepseek.com/chat/completions` | ✅ 预检直接回 `allow-origin` + `allow-headers` | ❌ |
| 自定义 | 用户自己填 | 取决于对方 | — |

智谱的实测细节：

```
OPTIONS /api/coding/paas/v4/chat/completions   → 200，但没有 Access-Control-Allow-Origin
POST    /api/coding/paas/v4/chat/completions   → 200，Access-Control-Allow-Origin: <你的 origin>
浏览器 fetch                                    → TypeError: Failed to fetch
```

POST 的响应带 ACAO，但**预检响应不带**，所以浏览器在预检阶段就拦掉了。DeepSeek 则是预检就回全套头，
所以它能直连——不需要代理，也就不需要部署任何后端。

### 面板上「服务商」点一下就换

换服务商 = 换端点 + 换默认模型（key 保留）。一家一家的 key 形态不同，所以还做了**错配检测**：

- 智谱的 key 形如 `xxxx.yyyy`（中间一个点）
- DeepSeek 的 key 形如 `sk-…`

拿 DeepSeek 的 key 打智谱端点，服务端只会回「身份验证失败（401）」——这句话对用户零信息量。
所以 401 时会先比形态：**「key 是「DeepSeek」的，端点是「智谱」· 换服务商」**。

> 这个错配是真实发生过的：用户配了 DeepSeek 的 key，但默认端点是智谱的，于是一路 401。

### 生产环境

只有「需要转发」的服务商才需要部署一个转发层。它可以是任何能转发 POST 的东西
（Cloudflare Worker / Vercel Function / Nginx），要求只有一条：**把 `Authorization` 原样透传**——
服务端不存 key，也就不需要信任服务端。用户也可以把端点改成自己的代理完整 URL。

> 小程序**不支持**：微信要求 request 域名提前在后台配置且要备案，不可能让用户自带。
> 所以小程序端 `aiLabel()` 显示「当前壳不支持」，**完全没有生成能力**——题库、建模库照常，画布照常能手动搭。这与「小程序做分发端」的定位一致。

## 4. key 的安全边界

- **BYO-key**：用户自己在「用户页 → AI 建模」里粘贴，存在本机 `localStorage`（键 `slogan.ai.v1`）。
- 存在**独立的 key** 里，不混进建模库——建模库会被导出/分享，凭据不该跟着走。
- **不进代码、不进构建产物、不进仓库**。仓库是 public 的，这一点没有例外。
  连测试脚本也只从环境变量读（`LLM_KEY=xxx node scripts/ai-check.mjs`），不写文件。
- 代价：每个用户得自己准备 key。这是零后端 + 免费的必然结果——内置一个 key 等于公开它。

## 5. 已知局限

| 局限 | 表现 | 现在的处理 |
|---|---|---|
| **会把「答案」填进参数** | 圆轨道题问「求最低点速度」，它把算出来的临界速度填进 `v0` | 提示词里写了「参数是输入不是答案」，但实测仍偶尔发生。**不阻断**——临界值恰好是演示最有用的状态，用户能拖滑杆 |
| **延迟 2–5 秒** | 一次读题要等几秒，课堂上有感知 | 生成时 toast 显示「AI 正在读题…」，成功后在提示里标耗时 |
| **偶发多填参数** | 题干没给质量，它也填了个默认值 | 参数被夹在可调区间内，不会崩；用户看左侧滑杆就能发现 |
| **只能选已有场景或拼基元** | 电磁、热学、光学、波、碰撞、传送带一律 unsupported | 这是设计，不是缺陷——不给错模型优先于覆盖率 || **思考模型会吃掉全部 token** | `content` 为空、全在 `reasoning_content` | 请求里带 `thinking: { type: 'disabled' }`；不认这个字段的厂商会忽略 |

## 6. 怎么验

```bash
npm test                                    # 31 项纯逻辑（提示词 / 解析 / 校验 / 三种模式）
node scripts/shots-bank.mjs                 # 19 项，含「坏 key 回退」和设置面板
LLM_KEY=xxx node scripts/ai-check.mjs       # 打真实接口，6 道题，看它到底怎么决定
LLM_KEY=xxx node scripts/ai-check.mjs --dump   # 额外打印抽到的参数
```

`ai-check.mjs` 不自己拼请求，而是调 `app.generateAsync`——测的是真实链路：
设置读取 → 提示词 → 请求 → 解析 → 校验 → 落库 → 打开画布。

2026-10-25 实测（glm-4.6，coding 端点）：

| 题 | 结果 | 参数 |
|---|---|---|
| 倾角 30° 斜面、μ=0.25、静止下滑 | `incline` | `theta=30, mu=0.25, v0=0` |
| 斜面 37° → 粗糙水平 1.5 m → 光滑圆弧 R=0.6 | **`chain` 3 段** | — |
| 半圆槽 M=0.5、m=0.2、R=0.4、可移动 | `trough` | `M=0.5, m=0.2, fixed=0` |
| 竖直圆轨道 R=0.5、恰过最高点 | `loop` | `R=0.5, v0=5`（见局限①） |
| 线圈在磁场中转动求电动势 | `unsupported`：电磁感应 | — |
| 水平传送带 | `unsupported`：传送带 | — |

**7/7 符合预期**。其中传送带和电机是「现成模型里没有、用 build 指令现搭」的——这是这次改造真正的增量。

### 实测：题库里标「暂不支持」的 7 道，AI 能建几道

2026-10-26 拿真实接口逐道跑了一遍（题库里 7 道历史标注为 unsupported 的真题）：

| 题 | 结果 |
|---|---|
| 2024 全国甲 13：汽缸与理想气体 | ✅ **建成** `gas` |
| 2024 全国甲 11：救护车追及与声速 | ⛔ 运动学计算，不是可演示的动力学过程 |
| 2023 全国乙 25：圆管、圆盘与多次碰撞 | ⛔ 需要多次碰撞模型 |
| 2024 新课标 11：两根绳缓慢下放重物 | ⛔ 共点力平衡，是解析题不是动力学 |
| 2024 新课标 13：电场与磁场中的带电粒子 | ⛔ 需要速度空间相图 |
| 2023 全国乙 24：三个点电荷的电场 | ⛔ 静电场叠加，是解析题 |
| 2024 全国甲 12：导轨、电容与电磁感应 | ⛔ 没有电磁感应模型 |

**7 道里 1 道建出来了**，而且拒的那 6 道理由都站得住——不是模型懒，是这些题本来就不是可演示的动力学过程。

这条实测带来两个决定：

1. **静态标注不能当闸门**。汽缸那道就是被历史标注拦掉的（规则解析时代建不了），
   用户配了 key 也点不了生成。现在所有题都能点「生成建模」，标注只作为提示语。
2. **列表和详情的状态改成「已建 / 未建」**。写「暂不支持」会让人不敢点，
   而且它随时可能过时——到底能不能建，问 AI 比问标注准。

## 7. 成本与体积

提示词（18 个场景的目录 + 规则 + 两个例子）约 6 KB 中文。**注意**：esbuild 默认 `charset: 'ascii'`，
会把中文转义成 `\uXXXX`——一个汉字从 3 字节变 6 字节，光这一项就让小程序包多出十几 KB。

所以 `scripts/build-miniprogram.mjs` 显式设了 `charset: 'utf8'`：包从 485.6 KB 降到 **458.8 KB**，
**比接 AI 之前（466.8 KB）还小**。顺带说明：这个 App 的界面文案全是中文，转义一直是隐形的体积税。

## 8. 计费

按次计费，一次读题约 1.5k 输入 + 200 输出 token。用户自带 key，成本由用户承担；
这也是为什么图片识别（多模态，单价更高）仍然没做。

## 9. 下一步

- **让 AI 也参与「怎么改」**：现在是选模型，之后可以是「把 θ 调到恰好不滑」这种指令。
- **失败样本回流**：把 `unsupported` 的题按类别统计，决定下一个该做哪个模型（现在只有 9 道真题的样本）。
- **抽参数的质量评估**：用 `gaokaoCases.ts` 的 9 道题做回归，比「看着对」可靠。
