# 场景集（Collection）：一个链接装多个模型

> 需求（2026-10-24）：老师课下准备好，课上点开；**不能一道题一个链接**，要一个链接装多个模型。
> 结论：**零后端可行**。实测紧凑分享串平均 117 字符，一个链接可装 6–8 个场景。
> 前提：只收「预置派生」的场景（自由画布场景塞不下，见 §4）。

---

## 1. 先给实测数据（不是估算）

我把 18 个预置场景都跑了一遍 `encodeShare`（记得设 `meta.preset`，否则会退回完整 JSON）：

| 场景 | `p1.` 紧凑串 | 完整 JSON |
|---|---:|---:|
| rampChain | 185 | 3,850 |
| arcChain | 183 | 4,466 |
| rampArc | 150 | 3,831 |
| orbit | 133 | 2,694 |
| incline | 123 | 2,989 |
| trough | 113 | 3,749 |
| loop | 107 | 4,182 |
| pulley | 74 | 2,969 |
| **平均** | **117** | **3,463** |

**两个关键数字**：

| 预算 | 上限 | 能装几个 |
|---|---|---|
| 小程序分享 path | ~1024 字符（二手口径，见 §7） | **约 8 个**（974 字符，很紧） |
| Web URL hash | 实际可到 64KB+ | **20 个以上**（2,340 字符） |

**所以「一个链接多个模型」在技术上不是问题，问题只在微信卡片的长度。**

---

## 2. 链接格式

```
c1.<nameB64>~<token1>~<token2>~...~<tokenN>
```

- `c1.` 前缀（`p1.` = 单预置、`s1.` = 单完整、`c1.` = 场景集）
- `nameB64`：集合名（base64url，可为空）——「第3章 临界问题」
- 分隔符用 **`~`**，因为 base64url 字母表是 `A-Za-z0-9-_`，`. ~` 都不在其中；`. ` 已被 `p1.` 内部占用，所以选 `~`
- 每个 token 原样嵌入，不重复编码（省长度）

示例（3 个场景，无名）：
```
c1.~p1.trough.eyJ0Ijoi...~p1.loop.eyJ0Ijoi...~p1.incline.eyJ0Ijoi...
```

**兼容性**：`decodeShare` 先看前缀，`c1.` 走新分支，`p1.`/`s1.` 完全不变——旧链接继续有效。

---

## 3. 不要按「个数」限制，要按「字节预算」装箱

token 长度从 74 到 185 不等，差 2.5 倍。**固定「最多 8 个」会在长 token 上超限**（8 × 186 = 1,488 > 1024）。

正确做法是**贪心装箱**：

```ts
function fitForShare(tokens: string[], budget = 900): string[] {
  const out: string[] = []
  let used = 12                     // 'c1.' + name + 余量
  for (const t of tokens) {
    if (used + t.length + 1 > budget) break
    out.push(t); used += t.length + 1
  }
  return out
}
```

- **小程序分享**：预算 900，装到装不下为止；超出部分在 UI 明说「微信卡片带了前 N 个，完整集合请用电脑打开」
- **Web 链接**：预算 8,000，基本用不完
- **不静默截断**：一定要告诉老师少了几个

## 4. 三个必须处理的边界

### 边界一：自由画布场景塞不进集合

`encodeShare` 只在「结构没变」时给 `p1.`。一旦老师加了组件/约束/判据，或者从空白画布搭的，就退回 `s1.`（2.4–4.5KB）——**一个就撑爆 1024**。

**处理**：
- 集合**默认只收 `p1.` 场景**，加 `s1.` 场景时在 UI 明确提示「这个场景较大，微信卡片放不下，只能用电脑打开」
- 集合里只要有一个 `s1.`，整个集合标记为 `webOnly`，小程序分享按钮禁用并说明原因
- **不要偷偷压缩**。用 gzip 压 5 个 `s1.` 场景 ≈ 4KB，仍然超 1024，白忙

### 边界二：微信卡片装不下时

| 情况 | 做法 |
|---|---|
| 全部是 `p1.` 且 ≤ 预算 | 正常分享，带全部 |
| 超出预算 | 按 §3 装箱，UI 显示「卡片含 6/9 个」 |
| 含 `s1.` | 禁用小程序分享，提示「用电脑打开完整集合」 |

### 边界三：列表顺序算不算「预设教学法」？

**不算，但要守住线。**

- **可以**：给集合起名、增删场景、拖动排序（为了好找）
- **不可以**：顺序播放、每步讲解词、课前/课中/课后标记、知识点串联

判据回到 `DECISIONS.md` §30 那条原则：

> 只提供「物理情境」，不提供「怎么讲」。

**集合是一个袋子，不是一个流程。** 排序是为了找得到，不是为了规定讲法。这个区别要写进代码注释，否则做着做着就变成课件了。

## 5. UI 形态（三个页面，都很薄）

```
① 集合列表页（打开 c1. 链接时）
   ┌──────────────────────────┐
   │ ← 第3章 临界问题    [编辑]│
   ├──────────────────────────┤
   │ 1  半圆槽：槽会被推走吗   │
   │ 2  竖直圆轨道：拖到多快…  │
   │ 3  斜面滑块：拖倾角…      │
   └──────────────────────────┘
   点任一行 → 进入场景；场景内左上角「← 返回列表」

② 场景页（不变）
   只是多一个「返回列表」按钮；从单链接进入时不显示

③ 老师端编辑（仅 Web）
   列表底部「+ 添加当前场景」「重命名」「删除」「拖动排序」
   「导出 .json」「复制链接」「分享到微信」
```

**小程序端**：只有 ① 和 ② 的只读版（`DECISIONS.md` §30：小程序不做编辑）。

## 6. 持久化：不靠后端，靠文件

老师「课下准备好」需要东西存下来。三个选项：

| 方式 | 成本 | 适用 |
|---|---|---|
| **链接本身** | 0 | 老师把链接存到自己的笔记/微信收藏 |
| **导出 .json 文件** | 0 | 一学期攒几个文件，换电脑能带走 |
| 云开发存储 | 19.9 元/月起 | 需要「打开就同步」时才上 |

**建议先做前两个**：链接 + `.json` 导出/导入。这两个完全零成本，而且解决了 90% 的「存下来」需求。

**只有当老师说「我换台电脑就找不到了」时，再上云存储。**

## 7. 待核实（我拿不准的地方）

1. **小程序 `onShareAppMessage` 的 path 上限到底是多少？**
   官方文档没写死；二手口径有 128 字节（可能指某个字段）和 1024 字符两种。**我用 900 作为保守预算，需要你在真机上试一次**：造一个 900 字符和 1000 字符的 path，看 `onLoad` 收到的 `options.c` 是否完整。这一步没做之前，§3 的预算只能算估计。

2. **`~` 在微信 path 里是否会被改写？**
   `~` 属于 RFC 3986 的 unreserved 字符，理论上不需要编码。但保险起见整体 `encodeURIComponent` 一次、`onLoad` 里 `decodeURIComponent`。**要实测**——特别是安卓旧版微信对特殊字符的处理。

3. **列表页是否需要缩略图？**
   缩略图能让老师一眼认出场景，但小程序里生成缩略图要么预渲染（成本），要么实时渲染（慢）。**建议第一版不要缩略图**，只显示序号 + 标题（标题已经在 `p1.` payload 的 `t` 字段里）。

## 9. 这个方案怎么回应「课堂太慢」

按 `DECISIONS.md` §30 的指标 **T = 从「手上有这道题」到「模型能拨」的秒数**：

| 场景 | 改之前 | 改之后 |
|---|---|---|
| 老师课下准备 5 道题 | 5 个链接、5 条消息 | **1 个链接** |
| 课上打开第 3 题 | 翻聊天记录找第 3 条 | **点列表第 3 行** |
| 发给学生 | 5 条消息 | **1 条消息** |

**注意：这不改变「第一道题的建模时间」**——T 的瓶颈仍然是「题目 → 模型」本身（图片入口未实现、生成后纠错慢）。

场景集解决的是**组织成本**，不是**输入成本**。两者要分开看，不要因为做了集合就以为 T 达标了。
