# 关键取舍与偏离（v1）

> 记录「为什么这么做」，以及哪些地方**没有照架构文档做**、为什么。
> 数字都来自本仓库的测试或 `npm run validate`。

## 1. 最重要的发现：半圆槽的核心结论是错的

交接文档（`physics-modeling-handoff.md` §二）说：

> 槽固定 → 小球能滑到右侧等高处；
> 槽可移动 → 水平方向动量守恒，槽被推着动、分走了一部分动能，**小球到不了等高位置**。

**仿真推翻了这个结论。** 在光滑半圆槽、小球始终不脱离槽的前提下：

- 小球到达右侧最高点时，相对槽的速度沿竖直方向（槽在该点的切线竖直），所以小球的水平速度等于槽的水平速度；
- 系统水平动量为 0 → 两者水平速度都为 0 → 此刻动能全部转化为势能；
- 于是 **h = h₀**，小球回到等高位置。

实测（`tests/acceptance.test.ts`）：

| | 小球最高点 | 与初始高度差 | 槽位移 | 水平动量 |
|---|---|---|---|---|
| 槽固定 | 0.9564 m | 0.00% | 0 | 不守恒（外部支撑力） |
| 槽可移动 | 0.9565 m | +0.01% | −0.265 m | \|p\| < 0.01，守恒 |

**产品决策**：不删掉这个场景，而是把它改成「推翻直觉」的场景。标题改为《半圆槽：槽会被推走吗》，文案直接写出「你以为球到不了等高，其实到了；变的是槽的位置」。这恰好是产品「原理验证」定位的最佳样本：**工具的价值不是确认课本，而是让你看见自己错在哪**。

如果要做「固定/可移动导致落点不同」的戏剧性对比，应换成**四分之一圆槽**（水平出口）：出口速度 v = √(2gR·M/(M+m))，落点差一个 √(M/(M+m)) 因子。这一版没做，列入 P2。

## 2. 轨道为什么不用碰撞链

架构 §3.3 要求「折线和圆弧一律用胶囊」。实测发现：**球在圆弧上用多边形/链碰撞会持续损失机械能**，且损失与步长无关、只与分段数有关：

| 分段 | 2 s 机械能损失 |
|---|---|
| 20 段 | 31% |
| 40 段 | 19% |
| 60 段 | 13% |

这是几何性的：每跨过一条弦，法向速度方向被投影一次，能量逐段损耗。细化到 1° 也只有 ~2–3%，而 40 次判据搜索要跑 40 遍场景。

**改为理想约束**：`track` 约束用 Planck 的 `DistanceJoint`（半径 = 轨道半径 − 球半径）把球心约束在圆上，每个子步读关节反力：

- `dot(反力, 指向圆心) > 0`：轨道在推球，正常；
- `< 0`：轨道需要「拉」球，物理上不可能 → 销毁关节，球脱离；
- 球脱离后向内运动；只有先**远离轨道 8 mm** 才允许重新接上（避免贴面抖动），再接上时把向外径向速度清零（完全非弹性撞壁）。

结果：临界速度误差从 3% 降到 **0.24%**（`tests/acceptance.test.ts` 的 34 次二分）。代价是轨道不再参与碰撞——所以轨道体只保留底座/支柱的 fixture，弧本身不生成 fixture。

这也解释了为什么架构文档 §5.3 说「洛伦兹力对步长敏感」是对的，但同一个道理对**接触链**同样成立：凡是「每步投影一次」的曲面接触，都会稳定地漏能量。

## 3. 洛伦兹力：不能当外力加

架构 §5.3 的写法是每帧 `applyForceToCenter(qv×B)`。实测 10 圈半径漂移 **+12.5%**（1/240、2 substeps），速度误差 +14%；减小步长只能线性改善。

改为**速度旋转**（Boris pusher 的纯磁场形式）：`θ = −(q/m)·Bz·dt`，直接旋转速度向量。速度模长严格不变，10 圈漂移 **0%**。

注意量级：真实比荷下回旋周期 ~1e-7 s，1/240 步长连一个周期都采不到。磁场场景必须用**教学比荷**（q/m ≈ 1）并在 UI 里明说，否则会得到一个物理上无意义的动画。

## 4. 投影公式里 z 的符号是反的

架构 §4.2：

```
v = (x·sinφ + y·cosφ)·sinε − z·cosε
```

按这个公式，竖直面里 **z 越大越靠下**——整个场景会上下颠倒。第一版截图里半圆槽是「∩」形，就是撞上了这个。

重推（相机在上方、屏幕 v 轴向上）：

```
v = base·sinε + z·cosε
d = base·cosε − z·sinε
```

反解也随之改为 `z = (v − x·sinφ·sinε)/cosε`。`camera.test.ts` 的 13 个往返/朝向测试锁住了这一点（往返误差 < 1e-9，且 z 高必须屏幕更高）。

## 5. 启动沉静期（settle）

形状刚好放在地面上时，Box2D 的位置修正会把物体顶起约 5 mm（linear slop）。对半圆槽这种「能量非常小」的系统，这会让机械能基准直接跳 5%，触发守恒判据误报。

处理：`world.settle`（默认 0.12 s）。这段时间：

- 能量类判据不取基准（`CriteriaRunner` 内部跳过 conserve）；
- 接触/脱离类判据**照常**从 t=0 开始判（否则低速小球一开始就脱离的情况会被漏掉）。

## 6. `params` + `layout()`：让 θ 这种几何参数也能用滑杆

架构要求「滑杆直接改 Scene，改完重新求解」，但 θ 一改，斜坡几何、滑块位置、初始速度方向全变，一个 JSON Pointer 改不动。

方案：场景带一个 `params: Record<string, number>`，滑杆绑到 `/params/theta`；预设场景带一个**确定性的** `layout(scene)`，在「重置 / 改参数 / A/B 克隆」时把 params 展开成几何。

- 分享出去的场景带 `meta.preset`，打开后仍然能认出预设，滑杆继续生效；
- 直接拖动物体**不会**触发 layout（否则会被弹回去），下一次改参数才重新展开——这个语义写在 README 里。

## 7. 判据的语义：不判对错

产品边界「不判对错」落到实现上：

- `CriterionResult.pass` 只表示「条件是否被检测到」，不表示「学生答对/答错」；
- UI 的 chip 用「已发生 / 未发生」「守恒 / 不守恒」，不用红绿对错；
- 临界搜索的结论是「v₀ ≈ 5.20 时翻转」，不是「你错了」。

## 8. A/B 用叠加而不是分屏（v4.1 已废弃，见 §18）

竖屏手机上分屏每边只有 170 px，看不清。做法：

- 同一相机、同一坐标系叠两层；
- A 用场景原色 + 蓝色实线轨迹；B 用 62% 透明 + 橙色虚线描边 + 橙色虚线轨迹；
- 右上角卡片给 A/B 两列读数（最高点 / 当前速度 / 判据状态），图表里两条曲线同图。

半圆槽的 B 槽「整体左移」正好是这个场景要讲的事，叠加反而比分屏更直观。

## 9. 精度档与采样

- 圆、矩形用精确形状（Planck Circle / Polygon），不做多边形近似；
- 圆弧、贝塞尔只在**渲染**上采样（teach 6°/16 点，verify 3°/64 点）；物理上弧是理想约束，贝塞尔转 chain；
- 渲染几何按 Shape 对象缓存（WeakMap），编辑时重建，渲染时不再细分。

## 10. 先做 Web 壳

交接文档写「先做小程序先上线」，但本机没有微信开发者工具，无法编译/真机预览。硬写一个小程序壳而无法验证，风险高于价值。

所以第一版把**平台无关的三层（core/physics/render/ui）做完整**，Web 壳只负责 canvas + 指针 + 分享。`@ui/app` 没有任何 DOM 调用，搬迁清单见 [MINIPROGRAM.md](MINIPROGRAM.md)。

## 11. 其它小取舍

| 决策 | 原因 |
|---|---|
| 时间步：斜面/平抛 1/240，轨道场景 1/960（effective 1/1920） | 轨道场景对能量误差敏感；固定步长仍保证确定性 |
| 拖动阈值 8 px 才触发「滚动」而不是「点开」 | 否则在手机上一划就进场景 |
| 选中物体时相机上移 55% 的面板高度 | 底部半屏面板会盖住地面附近的小球 |
| `maxSpeed = 30` + 每秒最多一条限速事件 | 防止数值爆炸，又不刷屏 |
| 分享用 URL hash（base64url + UTF-8 手写编解码） | 小程序没有 `btoa`/`TextEncoder`，手写一份两边都能跑 |


## 12. v2：3D 与搭建模式（v3 已回退，见 §13）

- **3D 的边界**：物理仍在竖直平面（x–z）里跑 2D；3D 是渲染/观察层。相机是正交轨道相机（yaw/pitch，yaw 限制 ±69°，pitch −10°…74°），物体沿 y 挤出，侧壁按世界法线打光——所以转动场景时明暗是稳定的，不是按边序号交替。没有上 WebGL/three.js：小程序包体和真机验证成本不划算，而且正交投影更适合教学测量。
- **默认侧视**：删掉 iso/top 预设，视图键只在 侧视 ⇄ 3D 之间切。3D 预设固定 yaw=0（地面不歪），要看侧面用「转动场景」工具自己转。用户说的「不要斜视图」保留为默认侧视，3D 是一次点击。
- **吸附**：`packages/core/snap.ts`。找最近表面点 + 法线：球按法线放 r，方块按切线转角（当前角度和表面差 >70° 就不硬转，避免把竖着的墙推倒）。拖拽时实时吸附，阈值 0.26 m；拖到没有表面的地方就不吸。自由画布画圆时也会先吸一次。
- **双击分类**：地形 → 物体 → 轨道 循环，删掉黑底分派条（用户反馈「选择模式一块黑色」）。画圆默认物体、其余默认地形。轨道分类只对圆弧/圆生效：找 r+0.9 内最近的小球，生成 track 约束并把球放到轨道半径上。
- **旋转手柄**：选中后出现在物体上方 58 px，按平面角计算，15° 内有 2.5° 磁吸。
- **相机不再按面板高度平移**：开关面板各移一次会让场景越漂越低；改成「选中/新建时只把物体顶到面板上方」。
- **空白画布尺度**：手机 110 px/m、桌面 235 px/m。之前按 5 m 默认范围取景，手机上 1.6 m 的斜面只有 100 px。
- **形状面板**：左侧工具栏只放 选择/转动场景/橡皮/平移，形状收进一个 3×2 面板（矩形、圆、三角/斜面、直线、圆弧、手绘），避免手机上竖排 10 个工具压到底部参数坞。


## 13. v3：回到 2D，补全力学

- **2D**：3D 轨道相机、挤出、视图切换全部下线，相机固定正交侧视。教学上侧视更好测量；3D 的交互/视觉成本没有对应收益（用户明确要求）。渲染改成平面渐变 + 描边 + 细高光，阴影只留地面。
- **外力**：`Body.appliedForce`（N，世界坐标）+ 可选 `appliedUntil`；属性面板给 Fx/Fy 滑杆（−20…20 N）。
- **弹簧**：不用 DistanceJoint 的软约束——实测能量漂移 ~10%。改成每子步施加真实力 F = k(l−l₀)（可带阻尼），并在监视器里补 ½k(l−l₀)²；守恒判据漂移 0.7%。绳/杆/铰链仍用关节（理想约束不做功）。
- **受力图**：Simulation 每步算 G/F/qE/T，渲染层画箭头；长度相对该物体的重力归一（拉力/重力可直接比），选中物体时标数值（N）。qE 只算匀强电场，并按区域门控。
- **连接工具**：点 A、再点 B 生成一根绳（锚点取点击处的局部坐标，绳长 = 两点距离）。
- **新场景**：弹簧振子、单摆、电场中的带电粒子。电场场景把重力设为 0（只研究电场力，场景说明里写清这个理想化假设）。
- **没做**：滑轮/传送带（需要专门的锚点 UI）、磁场预置（教学比荷的表述没定）、电势能（电场场景不做守恒判据）。


## 14. v3.1：组件检查器，去掉场景控制面板（v4.2 已清掉旧 controls，见 §19）

- **为什么去掉**：预设场景的"场景控制"把参数和物体脱钩了——μ 的滑杆绑在 `contactPairs[0].mu`，布局又用 `params.mu` 覆盖回去，所以拖不动；θ 和 v₀ 也是"场景参数"而不是组件属性。改成选中组件后直接改它自己的字段。
- **检查器**：`Body` 新增 `friction`（覆盖材质 μ，接触时若两边都有取平均，只有一边有就用那一边）；角度、速度矢量、质量、外力都在检查器里直接写 `Body`，不再经过 `Control`。A/B 仍用 `Control`（它需要两套值）。
- **长条地形**：静态/地形组件不再吸附（之前拖斜面会被吸到地面、角度归 0，就是"飞走"），也不显示旋转手柄；角度用检查器的 0.5° 滑杆微调，位置直接拖。
- **速度矢量**：大小 + 相对水平的方向两个滑杆；检查器实时显示 `v = … m/s · 方向 …°`，场景里选中物体的 v 箭头也标数值和角度。
- **状态栏**：没选组件时底部只留判据 chips、A/B、找临界、世界；世界面板放 g、场强 E、空气阻力。选组件时状态栏换成检查器。
- **遗留**：`Control` 的滑杆渲染代码还在（只有 A/B 在用，旧的 renderControls 是死代码），下一版可以删掉。预置布局在 A/B 时仍会重写部分组件字段（θ/μ/v₀ 已同步 params，其他字段可能丢）。


## 15. v3.2：编辑覆盖层、多外力、精简角色

- **编辑覆盖层**：检查器的写入同时记到 `scene.edits`（按 body/constraint id）。预置布局、A/B 克隆、分享解码之后都调用 `applyEdits` 把用户改的字段盖回去。这样 A/B 不再冲掉用户编辑，预置场景的紧凑分享也能带上编辑（结构变了才回退完整 JSON）。
- **多外力**：`Body.forces` 是可叠加数组，渲染用 `THEME.forceColors` 的调色板 + F1/F2 标签；检查器用彩色 chip 选力，再用大小/方向滑杆改。旧的 `appliedForce` 仍兼容。
- **精简**：材质滑杆去掉（摩擦已经按组件设，材质只影响预置的恢复系数）；模型只剩质点/刚体（固定 = 角色地形）；角色只剩地形/物体（轨道 = 地形 + 圆弧的「小球贴着轨道走」开关）。
- **地形贴地**：静态地形移动/旋转/绘制后用 `bodyAABB` 的最低点做参照，最低点 < 0 抬起来，< 0.18 吸到地面；物体仍吸附到表面。
- **同类地形合并**：连接工具点两块地形时，把它们的渲染轮廓烘焙成世界坐标的复合体（transform 取包围盒中心），形成一个连续地形；有约束/观测引用时拒绝，圆形拒绝。


## 16. v3.3：组合式斜面+圆弧、速度箭头、题目解析

- **斜面+圆弧为什么是组合**：如果做成单个组件，整条轨道只能有一个摩擦系数，而题目恰恰要求"斜面粗糙、圆弧光滑"这类分段条件。所以斜面、圆弧、水平段是三个 static 地形，各自设 μ；几何上用「圆弧在连接点与斜面共切线」保证小球平滑过渡。圆弧半径可在检查器里改，样式可切细线。
- **圆弧的半径**：`Body.shape.r` 直接改，body 的变换点是圆心（因而标签/选择锚点在圆心）；轨道连接用「让小球贴着轨道走」开关。
- **细线样式**：`appearance.style = 'solid' | 'thin'`；thin 只描轮廓、不填充，物理仍是同一条形状（视觉简化，不改变模型）。
- **速度箭头**：有 vector 观测者时沿用观测者；没有时，选中的动态物体在渲染层补一个 v 箭头，数值和角度写在同一标签里，拖端点改速度。
- **题目解析**：`packages/core/src/problem.ts` 是**离线规则解析**，不调用大模型：关键词定 6 类 archetype，正则抽参数并做单位换算，最后用预置的 `layout` 生成 Scene。它只适合"一段/两段、单条件"的题；多过程、临界讨论、连接体等复杂题会识别失败并提示，手动建模兜底。Web 用 DOM 弹层，小程序用 editable showModal。
- **测试题目**：目前 7 道代表性题目在 `problem.test.ts`（斜面+圆弧、斜面、平抛、单摆、弹簧、圆轨道、失败提示）；近十年高考真题数据集尚未导入，下一步可在 `data/problems` 放题干+期望 archetype/参数做回归。


## 17. v4：精密工作台界面

- **方向**：暖纸画布 + 炭黑框架 + 单一烧橙；标题宋体、数字等宽、1px 发丝线、无重阴影。深色只放在框架，画布保持纸色，保证物理标签/箭头可读。详见 `docs/DESIGN.md`。
- **选择页**：炭黑品牌区 + 宋体大标题 + 主 CTA；桌面 4×2 卡片一屏看完 8 个场景；手机横向卡、说明两行、编号在标题上方；悬停仅桌面。
- **场景页**：顶栏只留重置/播放；速度统一到工具轨；图表默认收起；状态条是 1000px 居中的悬浮控制台，动作带图标；检查器最大 1000px 居中，样式开关收进头部，模型/角色并排。
- **评审**：一轮独立、不打分。采纳了"降饱和物体色、滑轨对比、样式归组、居中检查器、收起空图表、动作用图标、统一 1×、手机说明换行/编号/去 hover"；未做直接输入数值和侧栏，原因记录在 DESIGN.md。

## 18. v4.1：不做 A/B，按题目假设建模

- **决定**：A/B 对照是**伪需求**，从产品里移除——状态条不再有 A/B，预置场景不再带 A/B 控制，双仿真/幽灵 B/AB 图表不再出现在界面里。
- **理由**：A/B 把「比较」做成了一个功能，学生容易只看两个动画而不建模；物理教学真正需要的是**先按题目假设定模型，再改一个条件看结果**。A/B 还会把「改了什么」藏在两个世界之间，反而增加认知负担。
- **替代**：
  - 预置场景按题目假设定默认：斜面滑块（矩形质点）、半圆槽槽可移动、平抛不计空气阻力、圆弧光滑；
  - 检查器可以直接改 μ、模型、半径、外力；
  - 解析器从题干识别「滑块/小球、滚动/纯滚动、光滑/粗糙、固定/可移动、空气阻力」，把假设写进 `params` 和 `scene.meta.note`，并在消息里列出「假设：…」；
  - 「找临界」保留：它是单场景的二分搜索（改变一个参数找翻转点），不是 A/B 双跑。
- **模型细节**：
  - 滑块 → 矩形质点，平动；小球 → 圆；「滚/纯滚动」→ 刚体圆球；
  - 2D 圆在 Planck 里默认是圆盘（I=1/2），现在按高中「小球」的假设改成**实心球 I=2/5**，滚动加速度 5/7·g·sinθ（原 2/3 是圆盘）；
  - 半圆槽按题干「固定/可移动」直接建一个场景，不再用 A/B 对照。
- **测试**：题目解析新增 5 条假设测试（滑块、纯滚动、粗糙圆弧、槽固定/可移动、空气阻力）；mp-verify 的 A/B 双跑改为题目假设解析 + 单场景水平动量；shots-build 的 A/B 编辑测试改为题目假设解析。

## 29. v5.2：产品定位从「通用建模工具」改为「题目 → 建模 + 手动兜底」

- **为什么改**：v4.5–v5.1 把产品做成“先选示例/画布，题目解析只是加速器”。真实使用里，老师或学生手里先有的是一道题，而不是“我想建个模”。继续堆预设/组件解决的是供给问题，没有解决**入口**问题。
- **新定位**：输入是题目（现在粘贴文字；后续图片识别、拍照），输出是一张形象、易懂、可运行的物理建模。**生成的是初稿，手动修改建模是兜底**。不是题库、不是课程、不是实验复现，不判对错、不做 A/B 对照。
- **不变的部分（不要动）**：Scene JSON 仍是唯一真源；生成物就是普通 `body / constraint / field / observer / criterion`；物理、判据、分享、找临界全部不变；不逐题加 preset；几何仍是相对模型尺寸；不能生成时必须明确拒绝。
- **变的部分**：
  - 选择页主 CTA 从「从空白画布开始」改为「题目 → 建模」，「从空白画布开始」降为次入口；首屏文案改为“把一道物理题，变成一张能拨动的模型”。

  - 题目弹层从“一个文本框”改为三入口：`粘贴文字`（可用）、`图片识别` / `拍照`（disabled，明确标“即将支持”，点击只说明未上线）。

- **生成契约**：`parseProblem` 是生成链路 v0（离线规则解析），返回 `{ scene, assumptions, used, warnings }` 或 `{ error, hints, unsupported }`。后续 AI / 多模态入口复用同一形状，UI 不感知生成器实现；不要在壳（Web/小程序）里另写建模逻辑。

## 30. v5.3 定位收敛：不做课件、不做讲法，小程序做分发端

- **三个决定**（2026-10-24）：
  1. **不做课件**。理由是位置已被占：NB 实验室可「一键插入」希沃白板（NOBOOK 官网 2014 起，2024 年仍宣传「不用频繁切换页面」），希沃活跃教师 700 万、累计课件 15 亿份、交互智能平板出货份额 44.5%。详见 `POSITIONING-REVIEW-COURSEWARE.md`。
  2. **小程序做分发端**，不承担备课编辑。备课在 Web（键鼠、大屏、能存文件）；小程序只负责「打开即场景」和「转发给班级群」。
  3. **不做「讲法」**。理由：每个老师有自己的讲课风格，把教学路径编码进产品等于替老师决定怎么讲。曾提过「一个模型 + 一组参数步进 + 每步一句话」的复用单位，**此方案作废**。
- **由此确立的一条产品原则（比上面三条更重要）**：
  > **产品只提供「物理情境」，不提供「怎么讲」。**
  >
  > 判据：任何新增功能，如果它在表达「先这样、再那样」，就不做；如果它在扩展「这个情境能被怎么摆弄」，就做。
  >
  > 这条原则会否掉很多东西（课件、讲法、教学步骤、知识点串讲、习题课流程），是有意为之。
- **一个必须接受的推论**：既然不做课件也不做讲法，「课堂即时建模太慢」这个问题**没有被产品结构解决**，只能靠**把建模本身变快**。
  - 所以下一阶段的核心指标不是留存、不是 UV，而是 **T = 从「我手上有这道题」到「模型在屏幕上能拨」的秒数**。
  - 目标：**课堂可接受 ≤ 10 秒；备课可接受 ≤ 60 秒**。当前 T 无法满足课堂（图片入口未实现，粘贴文字 + 纠错约 45–150 秒）。
- **T 的当前构成（估，未实测）**：

  | 步骤 | 耗时 | 状态 |
  |---|---|---|
  | 拍照/截图 | 3–5 s | 能做（`wx.chooseMedia`），但只产出一张图 |
  | 图片 → 文字/要素 | **∞** | **未实现**（弹层里是 disabled 占位） |
  | 粘贴文字 | 15–30 s | 可用 |
  | `parseProblem` 解析 | < 0.1 s | 可用 |
  | 生成后纠错（生成不对时手改） | **30–120 s** | 可用，但**这是被忽略的最大成本** |

- **三个抓手（按性价比排，不按直觉）**：
  1. **条件表单（零成本，5 秒，100% 成功）**——把「多过程链」已有的「阶段 + 参数滑杆 + 插入画布」模式，从「链」扩展成**并列主入口**：选情境类型 → 填 3–5 个参数 → 即时出模型。不需要 AI、不需要 OCR、不需要内容库、纯前端。它服务的是「老师心里已经有一个情境」的场景，而这恰好是「不预设教学法」原则下最自然的能力。
  2. **生成后纠错成本**——现在的语义是「生成错了 → 手动改」，改一次可能 2 分钟。改成**「假设可勾选」**：生成时把每个假设（滑块/小球、光滑/粗糙、固定/可移动、有无阻力）做成一行可点的 chip，点一下即时重算，比重新生成或手动拖快一个量级。`meta.assumptions` 已经是字符串数组，结构上只差把它变成可交互。
  3. **图片识别**——真正的 10 秒方案，但成本与「完全免费」冲突（OCR / 多模态按次计费，属 L2 变动成本档）。**建议推迟**，或只做「本地轻量 OCR 认题型 + 明确说识别不确定」，不做全量公式识别。
- **分发端（小程序）的边界**：
  - **做**：打开分享链接/卡片即场景；只读 + 可拨参数 + 可看判据；转发到群。
  - **不做**：编辑（拖拽/检查器/组件库）、账号体系（openid 足够）、云同步场景库、课程结构、教学步骤。
  - **一个待定**：学生端要不要「只读」？倾向**是**——学生误改后得到错结论，比看不到更糟。老师端（Web）保留全编辑能力。
- **不变的部分（继续有效）**：Scene JSON 唯一真源；生成物是普通组件；不逐题加 preset；不能生成时明确拒绝；`docs/GAOKAO.md` 的能建/不能建边界。
- **待验证（不写代码就能做的）**：找 3–5 个物理老师问一句「你上一次讲临界问题是怎么讲的」，**只为确认他们会不会在课堂上打开一个工具**，不是问要不要「讲法」。
