# Agent：给它什么手、什么眼、什么尺

> 这一篇是 2026-10-26 一整天讨论的收敛结果。回答一个问题：
> **要让 agent 自己建物理模型，需要给它什么。**
>
> 结论先行：**不需要更强的模型，需要给它手、眼、尺。** 而三样里只有"手"要真干活。

---

## 1. 先把产品说清楚

> **产品 = 一个可编辑的 Scene + 一套改写 Scene 的操作。Agent 和人类用的是同一套操作。**

这条一旦成立，"给 agent 什么工具"就等于"这个产品能做什么"，不是实现细节。

而现状是严重偏斜的：

| | 人类（`App` 的 private 方法） | Agent |
|---|---|---|
| 操作数 | **38 个**（50 处 `this.doc = {...}`） | **1 个**（整个场景） |
| 能改结构吗 | 能：增删物体、加约束、加场、贴轨道、合并地形 | **不能** |
| 能改参数吗 | 全部 | 只能改 `PARAM_META` 里的数 + 几个开关 |

**这就是自动建模覆盖率卡在 11% 的真正原因**——不是模型不够聪明，是**它没有手**。

真题里真正的变量是结构：161 种「场 × 约束 × 多过程」组合，前 30 种覆盖 76%。
而 agent 只能在 18 个模具里挑一个再调参，它连"在这里加一根绳"都做不到。

---

## 2. 手：操作层

### 2.1 工具要按 schema 切，不按 UI 按钮切

38 个方法是**UI 形状**的（`setBodyAngle` / `setBodyFriction` / `setBodyMass`… 每个对应一根滑杆）。
如果照原样暴露给 agent，那只是把"枚举 18 个成品"换成"枚举 38 个按钮"，表达力没变。

按 **Scene schema** 切，大概是 12 个工具：

| 工具 | 覆盖什么 |
|---|---|
| `addBody(shape, at, behavior, …)` | 圆/方块/三角/线/弧 全归它 |
| `setBody(id, patch)` / `removeBody(id)` | `setBody` 一个顶 10 个 setter |
| `addConstraint(type, a, b, params)` | 绳/杆/弹簧/铰链/滑轮/导轨/轨道/销钉/马达/传送带 全归它 |
| `setConstraint` / `removeConstraint` | |
| `addField(type, magnitude, direction)` / `setField` | |
| `addObserver(kind, …)` | 轨迹/矢量/图表/能量条 |
| `addCriterion(kind, …)` | 脱离/到达/碰撞/守恒 |
| `saveAsComponent(bodyIds, name)` / `insertComponent(id, at)` | 自举闭环 |

**12 个覆盖整个 Scene schema**，而且对模型来说工具越少越不容易选错。

> 注意：`addObserver` / `addCriterion` **连人类都还没有入口**——观测器和判据只能来自预置场景。
> 但这两样恰恰是"可演示"的核心：agent 建了模型却没有判据，等于建了个只会动的动画。

### 2.2 参数不能是绝对坐标

```ts
addBody({ shape:'circle', at:{ x:2, y:3 } })   // ❌ 模型不知道 (2,3) 在这个场景意味着什么
addBall({ on:'ramp', near:'top' })             // ✅ 语义定位
```

模型不知道场景尺度是 1 米还是 10 米，也不知道 `ramp` 在哪个方向。给绝对坐标的结果是：球悬在半空、方块埋在地里。

这个能力已经有了——`core/ports.ts` 的端口 + `core/snap.ts` 的吸附。工具参数应该走这条路。

## 3. 眼：两种回读，成本差一百倍

| 回读 | 内容 | 成本 | 什么时候用 |
|---|---|---|---|
| **结构摘要** | 几个物体、约束图是否闭合、包围盒、每个物体的角色/材质/参数 | 几十 token | 每次操作后都看 |
| **截图** | 一帧渲染出来的图 | 一张图 ≈ 上千 token | 建完、或自检失败时 |

截图这条路在本项目里意外地便宜：`render` 包零 DOM 依赖，`renderScene()` 是纯函数，给个 ctx 就能画；
Playwright 已经装了，离屏截图不用引入任何新东西。

**但要认清它的边界**：截图能看**结构**（球悬空了、轨道没接上），看不出**物理对不对**。
有实证：LLM 判断仿真结果不如人工（见 [RESEARCH.md](RESEARCH.md) §5）。所以"像不像那道题"的一半能靠图，
"对不对"必须靠尺。

---

## 4. 尺：校验 + 验算

这是最被低估的一项，而且**能力已经存在，只是没包成工具**。

| 手段 | 检查什么 | 现状 |
|---|---|---|
| 结构校验 | 悬空引用、悬空端口、退化几何、过约束 | ✅ `core/validate.ts` |
| 物理验算 | headless 跑一遍：NaN、穿模、守恒漂移、判据是否触发 | ✅ `core + physics` 零浏览器依赖，`tests/acceptance.test.ts` 就在 Node 里跑 |

「已经能跑」这句是关键：agent 可以**自己跑一遍再交付**，而不是等你打开看到球穿墙了才发现。

这会改变整个交互模型：从「生成 → 人检查」变成「生成 → 自检 → 修 → 交付」。

## 5. 创造不止于组合——但分三层

用户的原话：「agent 创造是基于用户告诉它的物理场景……如果现有组件能满足就不用造了，如果满足不了，必须从头造出来，且可以沉淀。」

这是对的，但要分成三层，因为**处理方式完全不同**：

| 层 | 判定 | 例子 | 处理 |
|---|---|---|---|
| **T1 缺打包** | 用基元拼得出来 | 传送带、电机、阿特伍德、双球+绳 | **当场造**：拼出来 → 沉淀 |
| **T2 缺参数** | 基元在，但缺一个参数 | 摩擦随速度变、静/动摩擦分离 | 给基元加参数 |
| **T3 缺机制** | 基元拼不出来 | 浮力、变质量、热传导 | **造不出来** → 诚实报告 + 记缺口 |

**T1 是主战场。** 传送带就是证据：组件库里没有，但它不需要新物理——

```
BodyKind 早就有 'kinematic' → 传送带 = 静态线 + 表面切向速度 + 摩擦
电机 = 铰链 + 马达参数（planck 原生有 setMotorSpeed / setMaxMotorTorque）
```

所以「组件库里没有」≠「表达不出来」，绝大多数是**没打包的模式**。

T3 的处理不是"不许造"，而是**要能说清缺什么**，产出结构化缺口：

```json
{ "missing": "浮力", "why": "需要按浸没体积积分的浮力，现有基元无此机制",
  "neededBy": "2024 全国甲 13 题", "workaround": "可先用恒力近似" }
```

这些缺口攒起来就是路线图的输入——哪类机制被最多题需要，就先加哪个。

### 一条硬边界：创造止于组合，不止于类型

不能让 agent 定义**新的 shape 或新的 constraint 类型**。因为类型是物理层的契约——
planck 不认识 `type:'conveyor'`，仿真直接崩。

- ✅ agent 可以决定"这里有三个刚体、两根绳、一块斜场"
- ❌ agent 不能决定"我要一种新东西叫传送带"

基元集本身会长，但长法是**加一个基元 + 物理实现 + 测试**，不是加一个成品。

## 6. 自举：工具集能自己长

如果 agent 能造 + 能沉淀，那**工具集是会生长的**。第一次遇到「双球 + 绳 + 斜面」要拼 5 步，
存成组件后下次 1 步。

```
基元工具（造） → extractComponent（沉淀） → 组件库（复用） → 下次一步完成
```

后两环已经有了（`extractComponent(scene, bodyIds)` / `instantiateComponent`），缺的是第一环和**参数槽**。

### 沉淀必须带参数槽，否则自举失效

`SavedComponent` 现在存的是**冻结快照**（坐标烘死在 body 里，没有参数）。

对人类够用（人记得住自己要改哪个数），但：

> agent 造了「v=2 的传送带」→ 沉淀 → 下一道题是 v=3 → 库里那个用不了，得重造。

结果就是「每个具体实例一个组件」，40 个上限瞬间爆掉。

**所以 agent 的沉淀产物不该是冻结快照，而是"带参数槽的可复用造法"**：

```ts
paramSlots: [
  { key:'v',  label:'传送带速度', unit:'m/s', min:0, max:10, path:'bodies.1.velocity.x' },
  { key:'mu', label:'带面摩擦', min:0, max:0.9, path:'contactPairs.0.mu' },
]
```

关键判断：**参数槽不需要 `layout()`**。`layout` 只在"参数改变几何"时才需要（θ 改变斜坡形状）。
而绝大多数参数是**数值行为**（速度、摩擦、质量、k、电荷），改它们不动几何，只是往路径里写一个数。

至于"参数改几何"那类（比如可调板长），结论是：**别沉淀成组件，让 agent 每次重造**——
反正重造只是改几个点的坐标，比维护一个 layout 函数便宜。

## 7. 权限分层：运行时只给数据，开发时给代码

| 层 | 给什么 | 表达力 | 能存/分享/编辑 | 结论 |
|---|---|---|---|---|
| **L1 数据** | 基元 + 参数（现在） | 组合空间 | ✅ 全部 | 主体 |
| **L2 力法则枚举** | 加 variant（浮力/变质量/速度相关摩擦） | 覆盖大部分 T3 | ✅ 全部 | **该做** |
| **L3 受限表达式** | `F = -k(x-x0) - c·v` 这类表达式树 | 接近任意力 | ⚠️ 可存，但没滑杆 | 后手 |
| **L4 引擎直连** | 任意 JS / planck API | 无限 | ❌ 全塌 | **不做** |

### 为什么 L4 不做：它会同时打掉六样东西

Scene 是 JSON 这件事，支撑着：分享串 `p1.`/`s1.`、建模库、撤销、判据 headless 跑、
4 套截图验收能复现、小程序端（不能 eval）。

一旦 agent 的产出里含**代码**（比如一个 per-step 力回调），这六样同时塌掉。
而且还有更隐蔽的损失：**用户改不了**——检查器改的是数据字段，一段回调函数没有滑杆可调。

### 为什么 L3 也不急：表达式树才是"约束下表达"的正确形态

"只允许调用某些函数的 JS"听着自然，但会带来三个麻烦：

| 问题 | 受限 JS | 表达式树（JSON） |
|---|---|---|
| 解析 | 要 parser（或 eval + 沙箱） | 本来就是 JSON |
| 编辑 | 给 `0.5*v.x + k*(x-x0)` 里的 `k` 一根滑杆，得反查 AST 再改写 | 每个叶子就是字段 |
| 校验 | 运行时才知道炸 | 类型层面就挡住 |

**"在约束下表达"的本质不是限制语法，是限制类型。** 表达式树把这件事做成了结构性的。

## 8. 现在缺什么（按性价比排）

| # | 缺什么 | 为什么重要 | 状态 |
|---|---|---|---|
| 1 | **属性表 + 面板表驱动** | 检查器面板原来是写死的（353 行、12 根滑杆）。agent 造了带马达的东西，也没有那根滑杆 | ✅ `core/body-fields.ts` |
| 2 | **组件参数槽** | 没有它，agent 造一次就得重造一次，自举失效 | ❌ |
| 3 | **判据 → 动作** | 现在判据只检测不动作，所以"绳断了球飞出去"表达不了 | ❌ |
| 4 | **op 层**（12 个工具） | 目前只有 build 子集的 3 条指令，够用但不完整 | ⚠️ 部分 |
| 5 | 截图回读 | 补上"像不像那道题"的判断（看不出物理对不对） | ❌ |
| 6 | 图片读题（OCR/多模态） | 唯一需要真花钱的外部服务；T 从 60 秒降到 10 秒的唯一路径 | ❌ |

第 1 项已完成：`BODY_FIELDS` 一张表管三件事——面板渲染、面板高度、泛型 setter。
加一个属性从「改 UI + 改高度算式 + 补 setter」变成「加一行表」。
顺手补上了原来**根本没有滑杆**的三个属性：质量、线性阻尼、角速度。

## 9. 外部参照

这块有 25 年的成熟答案，但解决的不是我们这个问题。详见 [RESEARCH.md](RESEARCH.md) §5：

- **Modelica**：组件 + 连接器 + connect 语句，参数是一等公民。但它没有"题目"这个输入。
- **Base Modelica**：社区为了机器可读专门做了简化子集 → **证明"给 agent 一个子集"是被验证过的路线**。
- **LLM + Modelica 的实证**：零样本生成不出可执行代码；精提示后 83–100%；**LLM 判断不了物理对不对**；
  从零"vibe coding"= plausible 但不 trustworthy，在受信库上配置 = decision-grade。
- **Physion**（最接近我们的产品）：画形状 + 属性面板 + **给物体挂 JavaScript**。
  它用脚本换表达力，代价是用户改不了——而它官网还写着"即将支持自定义滑杆"。

**空位还在**：Modelica 给工程师建复杂系统，Physion 给用户搭沙盒，都不解决"题目进来、模型出去"。
